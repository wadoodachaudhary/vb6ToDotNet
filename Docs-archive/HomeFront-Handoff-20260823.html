This is the single most confusing part of the setup. There are two sets of clones, and you never push from the ones you edit.

Do not git push from a source repo

Their origin remotes are stale or nonexistent — HomeFrontPB's points at a repository that isn't there. Commit locally in these, then let the deploy script publish. Pushing from here either fails or lands in the wrong repository.

Deploy staging clones — what actually ships

The script rsyncs each source tree into a staging clone and pushes from there. These live under VBToCSharp/HomeFront/Deploy/repos/:

hyphen-pb is the one that matters. It is where the team's merge requests land, where QA/UAT deploy from, and the only repo with an R1-UAT branch.

FlexKit is consumed two different ways

In your working tree, HomeFrontPB and HomeFront reference FlexKit as a live ProjectReference, so FlexKit edits flow in on the next build with no repack. The deploy script temporarily swaps that to a PackageReference against a packed .nupkg in local-packages/, builds to verify, and pushes that form. Your working-tree csproj is never modified.

Consequence · merging upstream csproj changes

If an MR changes HomeFrontPB.csproj, merge the change in by hand — never copy the file wholesale from origin/main, or you replace your ProjectReference with the deployed PackageReference and FlexKit stops flowing into local builds.

04The deploy sequence

This runs in order, every time. It is genuinely a sequence — later steps depend on earlier ones — so the numbering here is real, not decorative.

  1. Pull hyphen-pb origin/main firstFetch, list commits you don't have, and apply them into the local tree. The deploy is an rsync — anything upstream that isn't also local gets reverted on push. Mirror page changes to the other app; hand-merge the csproj.
  2. Verify sync-pair parity, then commit all four reposHomeFront and HomeFrontPB are a sync pair; the same fix belongs in both. Confirm the edits match before committing.
  3. Bump FlexKit and repack — only if FlexKit source changedBump the version in FlexKit.csproj, dotnet pack, replace the nupkg in HomeFrontPB/local-packages/. Skip entirely when FlexKit is untouched.
  4. Build every affected solutionHomeFront.sln and HomeFrontPB.sln always; add FlexCore.Showcase.sln when FlexCore changed. All must report 0 errors.
  5. Run the deploy scriptbash tools/deploy_to_repos.sh — resets each staging clone to its remote, rsyncs, swaps the FlexKit reference, build-verifies, commits and pushes.
  6. Verify the protections survived on origin/mainAzure token placeholders present, appsettings.Development.json still 97 lines, csproj publish-exclusion intact.
  7. Merge main into R1-UATConfirm the five disabled security toggles and env config are intact, build-verify the merged tree, then push.
  8. Publish FlexCore to NuGet — only if FlexCore changedCheck the latest published version first, bump above it, pack, push, then mirror the bump to GitHub.

05Standing rules that will bite you

Critical · never push local appsettings

The remote owns environment config. origin/main carries Azure DevOps token placeholders — Server=#{Database.Server}# — plus a 97-line appsettings.Development.json holding the auth cookie name, Serilog sinks, an InternalTools allow-list and Cognito settings. This machine carries localhost,1433 / sa and a stripped logging stub.

Pushing local over that replaces the placeholders with localhost and breaks QA, UAT and UAT-Hyphen simultaneously, while deleting the Cognito and Serilog config. This is now enforced by ENV_CONFIG_EXCLUDE in the deploy script — do not remove that exclusion. Real environment changes go in the pipeline variables, not here.

Sync pairs

HomeFront ↔ HomeFrontPB — the same migrated form lives in both (Components/Pages/Migrated/F*.razor vs flat Components/Pages/F*.razor). A fix in one belongs in the other. The only expected difference is HomeFront's extra @namespace line. FMain.razor is the exception — it carries ~1,700 lines of long-standing drift, so hand-apply there and never copy wholesale.

FlexKit ↔ FlexCore — not auto-synced (owner directive 2026-07-25). They are allowed to diverge. Sync only when explicitly told.

Hands off

FAssembly gItems — do not change that grid's behaviour or settings. It is finished, and a past change caused a major regression.

HomeFrontPOC — archived. Never build, edit, deploy or sync it. HomeFrontPB is the active app.

Crystal report XMLs — read-only. Fix at the loader or host-service level.

Engineering rules

VB6 fidelity is the prime directive. Read the matching .frm/.bas under HomeFrontVB6/ before changing a migrated F* page — most bugs are translation errors, not design flaws.

Grid columns come from AppGridLayout, never hardcoded. All UI primitives come from FlexKit — a raw <input> or <div> modal is a red flag. Minimise JavaScript — it needs a DOM-only justification, a tiny lazy import and a graceful fallback. Never interpolate user values into SQL.

The owner runs the app. Do not auto-start dotnet run; stop any session you were explicitly asked to start.

Other developers — chiefly Irfan Afzal — commit directly to both main and R1-UAT. Always fetch before assuming a branch is where you left it.

Two traps this cleanup exposed

The pipelines delete what is not in the package. All three carry RemoveAdditionalFilesFlag: true, so removing tickets from the repo would have wiped every environment's feedback history on the next run. Each pipeline now passes a matching skip rule:

AdditionalArguments: '-skip:objectName=dirPath,absolutePath=wwwroot\\tickets -skip:objectName=filePath,absolutePath=wwwroot\\tickets'

An rsync exclusion protects a path from deletion. Adding something to RSYNC_EXCLUDE stops --delete touching the staging clone's copy — so the removal never reaches the remote. A new exclusion needs a one-time git rm in the staging repos; after that it is self-sustaining. This bit twice during the cleanup, caught both times in post-deploy verification.
