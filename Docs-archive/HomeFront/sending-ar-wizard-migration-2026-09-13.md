## HomeFront Changes (2026-09-13, corrected 2026-09-30)

- [FSendingWizard](/Users/wadood/projects/VBToCSharp/HomeFront/MobileSource/HomeFront/Components/Pages/Migrated/FSendingWizard.razor:37) uses FlexKit `WizardControl` for its header, step content and navigation. The five selection lists are `GridControl`; radio buttons, checkboxes and the Finish progress indicator are FlexKit controls. The printer drop-down, the determinate progress bar and the read-only processing log were removed on 2026-09-30: they were stubs that never printed or logged anything.
- [FExportAREstimates](/Users/wadood/projects/VBToCSharp/HomeFront/MobileSource/HomeFront/Components/Pages/Migrated/FExportAREstimates.razor:28) also uses `WizardControl`. Its posting/review table is a FlexKit grid. The loading indicator uses `ProgressBarControl`, and the report link is a keyboard-focusable FlexKit button styled as a link. The missing accounting icon was replaced with the existing posting icon.
- Both use the established compact light-grey wizard styling. There is no custom wizard footer, HTML data table, modal overlay or new application JavaScript.
- AR columns use `GridLayoutPresenter` with the exact VB6 identity `FExportAREstimates.gData`: saved order, captions, widths and visibility are honored, and a missing layout shows `[gData FALLBACK]`. AR's internal EstAssemblyID is not exposed; the posting-selection affordance is independent of saved data columns.
- The Sending Wizard reads **no** AppGridLayout. HFSend never did (the lists are its design-time `gData(1..5)` columns filled by ordinal), so the 2026-09-13 `FSendingWizard.gData.{1..5}` lookup and its fallback were a web invention and were removed on 2026-09-30. See "Screen parity" below.
- AR navigation stays asynchronous. AR review selects one batch, including through native grid keyboard selection. Invalid selected estimates still disable Next. Back remains available on the pre-operation final page. Sending navigation is described below.
- The 2026-09-13 pass needed no shared FlexKit source change: these are host integrations of existing controls. The 2026-09-30 pass added one FlexKit change, mirrored to FlexCore: `MdiHost` cascades a per-pane `CloseThisWindow` (`Func<Task>`) beside `SetPageTitle`, so a page closes its own window (see "Close behaviour"). No FlexCore-to-FlexKit copying, HomeFrontPB edits, database/schema changes or deployment actions were performed.

### Selection

- Every PO list, count and Finish uses the exe's filter (0xcd6c): `ISNULL(IsTBDVendor,0)=0 AND Status<>'Pending' AND Cancelled=0`, with `Delivered` 0 (send new) or 1 (resend), in the session division. A NULL `Status` or `Cancelled` is excluded, as in the exe. The launcher's job and the rows ticked on earlier steps narrow it; a step with nothing ticked selects nothing.
- A launch with PO numbers (0xccb0) selects exactly those POs, with no `Delivered`, job or step filter, and opens directly on Ready (`Form_Load` 0x426cf7). Back is disabled for the single-PO Manual PO send (`SpecifiedPOsOnly`, 0x427a22); any other hand-off drops its list on Back and restarts at Task as a normal run, keeping the job (0x42de69). An empty Assign TBD list selects nothing, never every PO.
- Every value is a bound parameter. A selection above 2,000 bound values shows "Too many rows are selected for one run. Narrow the selection on an earlier step." and stays on the current step; on the Assignment page, which has no earlier step, it reads "N purchase orders are too many for one run. Send them from Send purchase orders in smaller selections." A list that fails to load shows "The list could not be loaded."; a failed Purchase Orders load selects nothing.

### Finish

- SendPO is checked again before anything is written.
- PO and NOI: the rows are the exe's `SendPOs` select over the whole selection, limited to a non-blank `POFormat`. Each format's XML (`wwwroot/resources/Estimating/PO Formats/xml/<format>.xml`, a Crystal XML `<Report>`) must open before anything is stamped; the POs of a format that cannot be opened are not marked sent, with one warning per format (`SendPOGroup` opens the .rpt before its stamp, frm:1658 / frm:1812).
- Stamp: `POMaster.DeliveryDate = GETDATE()` for the remaining POs, scoped to the session division, in one transaction (chunks of 1,000). Resend overwrites an existing date. Only `DeliveryDate` is written; `ReDeliveryDate`, recipient, method and address are untouched. A PO with no PO format is never marked sent (frm:1644). Not reproduced: the legacy NULL-format grouping quirk (frm:1587) and per-group transport failures (the web stamp is all-or-nothing).
- Print set: POs whose method is print (0) or fax (2), or whose address is blank (frm:1646-1647), open in the report viewer after the wizard closes as independent documents, one per supplier group (`PrintDocumentKey`: the raw delivery method, delivery address, PO format and vendor, frm:1587, which breaks before SendPOGroup's frm:1646-1647 downgrade; a NULL and a blank address are one group; the `SendPO_CCPrjMgr` PM-email break of frm:1572-1577 is left out under D1) in the SendPOs run order (the select's own `ORDER BY DeliveryMethod, DeliveryAddress, VendorDesc`, frm:1577/1579, exe 0xd19c, with no re-sort in C#; SendPOGroup frm:1607-1815 opens one report per group), each with DivisionID and its PO list and labelled "<VendorDesc> - <PONumber>" or "<VendorDesc> - n purchase orders (first, second, ...)" (a vendor without a description is labelled by its code); a group over 1,000 POs is split into consecutive entries and each adds " (a-b of n)". The Ready page's document count uses the same key. `FRptViewer` shows the batch's chooser caption, "Document" here; the Issue POs and Manual PO previews keep "PO format". The user prints or saves as PDF there (D1). If the viewer cannot be prepared after the stamp, an error says the POs were marked sent but the ones set to print could not be opened.
- Email POs with an address are marked sent and not opened; no email is sent (D1).
- Nothing sendable (no selected PO has a format that opens): nothing is stamped and the wizard closes with no message beyond any per-format warnings. Success closes silently (legacy unloads with no message). A stamp failure shows an error, stamps nothing and keeps the wizard open.
- RFQ: one UPDATE sets `vendorbids.SentDate = GETDATE()` for the selected bids (joined to `RFPs` and the division's vendor row, skipping RFP 0 and a blank vendor), then closes silently. No print set.

### Close behaviour

- FlexKit `MdiHost` cascades, per pane, `CloseThisWindow` (`Func<Task>`) beside `SetPageTitle`; it raises the host's `OnCloseRequested` with that pane's window id, so `FMain.HandleCloseRequestAsync` runs the close guard and removes that window whichever tab is in front. `FSendingWizard` and `FTBDAssignmentWizard` close through it; `ParentNavigate("")`, which closes the active window, is the fallback without the cascade, and a page opened by URL falls back to `/main`. Hosted in the Assign TBD window the wizard closes that window (D4).
- Finish closes the wizard first and opens the report viewer after the close completes, so the viewer is in front whether the wizard was in front or in a background tab.
- FMain: a guarded close brings the asked window to the front; a refused close leaves it in front (the send question or the refused-changes list stays visible); a completed close returns to the tab that was in front before, or to Home when none was. Closing the Assign TBD window with unsaved assignments asks Yes/No/Cancel (frm:236-238); Yes commits, and when it hands off a tab close stays on the send question while an application close goes on.
- The other MDI-only pages use the same cascade; pages also hosted inside another page's pane keep `ParentNavigate("")`. Both lists are in the app's `CLAUDE.md` (2026-09-30 section).

## Existing Boundaries

This is not complete HFSend delivery parity. Finish records the send in the database and opens the POs set to print in the web report viewer; it does not print unattended, email, fax, text or post to accounting (D1). NOI has no document of its own and runs as a PO send (D2). The AR accounting adapter and report-opening behavior were not redesigned. Desktop external accounting and web reporting/export differences remain intentional boundaries for separate work.

The current HomeFront routes remain `/po-sending-wizard`, `/po-sending-wizard/PO`, `/po-sending-wizard/NOI`, `/po-sending-wizard/RFQ`, and `/export-ar-estimates`. Existing entry points continue to resolve to these same two page classes; the Assign TBD continuation renders `FSendingWizard` inside the `FTBDAssignmentWizard` window rather than navigating to a route.
