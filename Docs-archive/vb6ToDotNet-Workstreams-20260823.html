Companion to the HomeFront Handoff

vb6ToDotNet Workstreams

Four sessions run in parallel on this machine, and they are not independent — they sit in two lanes separated by a hard approval gate. Knowing which lane a change belongs to is what stops an untested library edit reaching every host app.

The two lanes

Everything reduces to one question: does this edit reach a user on the next build?

Bench lane · risk absorber

FlexKitTester → FlexCore

Nothing here reaches a user. FlexKitTester references FlexCore, never FlexKit. This lane exists to absorb risk before it can touch production.

Approval gate

Two separate approvals. Build and verify on the bench → STOP and report → wait for the owner's tested go-ahead → only then port.

Live lane

FlexKit → HomeFront · HomeFrontPB · GhostWriter · GhostWriterLLM

All four hosts consume FlexKit by ProjectReference, so an edit here lands in every one of them on the next build. There is no staging step.

The gate is a hard rule, not a preference

Owner rule, 2026-08-19, stated mid-port of the zoom feature. Anything developed in FlexKitTester → FlexCore stays there until the owner has personally tested it on the bench and given an explicit go-ahead.

"Implement on the tester, then bring it to the apps" means two approvals, not one. If a port has already happened prematurely, reverse only your own edits — never git checkout files in the app repos, which may carry unrelated uncommitted work.

Divergence is often correct

FlexKit and FlexCore are allowed to diverge and are not auto-mirrored (owner directive 2026-07-25). A feature in one and absent from the other is frequently the intended state. Before concluding something is missing, ask which lane built it and whether the gate has been passed.

Ports completed: row virtualization (2026-07-26), the callback cache, the GridPerformanceMode enum, grouped-grid windowing, and app-wide text zoom (FlexKit 2026-08-22, apps 2026-08-23). Also ported: the grid-control.js drag-band outline, FlexKit → FlexCore on 2026-08-29 (FlexCore 0.2.23) — a surgical three-site port; the two files still diverge by ~140 lines. Still bench-only: row-selection recommendation 1.

FlexKit Tester — the sandbox

VBToCSharp/HomeFront/FlexKitTester, served on port 5299. All repro and bench pages go here. A repro once placed in GhostWriterLLM was reverted immediately.

Every new tester page needs @rendermode InteractiveServer

Without it the page renders static SSR: rows appear normally, every click and keydown is dead, and there is no error anywhere to tell you why.

FlexKitTester references FlexCore. A FlexKit-only behaviour difference therefore cannot be reproduced there directly — either apply the change under test to FlexCore as well, or test through the real apps — which you run and test yourself (corrected 2026-08-26), shutting every server down afterwards.

The PM-entry latency bench

A 12-row replica of FProjectManagers built to A/B ServerBacked against ClientBuffered text editing under latency. Two mechanisms worth knowing:

  • Latency injection — BenchLatencyHubFilter : IHubFilter delays every inbound circuit message process-wide, so it affects all tester tabs; reset to 0 on dispose. A real-wire alternative exists: tools/latency-proxy.py --listen 5298 --target 5299 --rtt 150.
  • The discriminator metric — "server keystrokes" counts input events reaching the document bubble. ClientBuffered stops propagation at the element, so this counts exactly the ServerBacked per-key dispatches. At 150 ms and 8 keystrokes: ServerBacked 8 server keys, ClientBuffered 0.

Browser-pane automation cannot test editing keys

Synthetic keys from the browser tooling never trigger native editing commands. Backspace, Delete and Cmd+A arrive as keydowns but delete and select nothing — no beforeinput fires — and type inserts text without per-key keydowns. Character keys and Enter behave normally.

To clear or replace a field in that pane: set input.value, set dataset.fxUserTyped='1', dispatch a bubbling InputEvent, then send a real Enter.

Restart the dev server after any library rebuild

A running server holds the assembly it loaded at process start, and the launch configs use --no-build — so rebuilding FlexCore or FlexKit changes the DLL on disk but not what the browser is served.

The symptom is brutal: the owner tests fix after fix and reports "no difference" for hours. On 2026-08-16 the tester was serving a build from 08:11 while the rebuilt DLL had long since moved on. Nothing was wrong with any of the fixes.

Verify the served build marker, not the built one. A marker unchanged between two tests means a stale process — say so immediately instead of theorising about the code.

Application-wide zoom — shipped

Live on main and R1-UAT.

It was built and verified on 5266 on 2026-08-19, then rolled back under the gate rule before being re-approved — which is why older notes describe it as bench-only. app_wide_text_zoom.md is now a record of what was done, not a plan.

Architecture worth carrying forward

  • ZoomService is registered AddScoped, per circuit. A singleton would leak one user's zoom across every session — the same class of bug as the static per-user state leak.
  • PageControl resolves it lazily via IServiceProvider, so hosts without the registration see zero change.
  • Only the outermost PageControl publishes the scope. It cascades itself so nesting is detectable; a nested scope re-declaring the em base would compound the factor.
  • The scope sets --fx-zoom plus font-size: calc(1em * var(--fx-zoom,1)). The em base is what makes the inherit chain scale — the variable alone only moves explicit calc rules. The owner caught this on the bench.
  • Layout hosts outside any PageControl publish the scope themselves — otherwise dialogs and toasts render unzoomed beside a zoomed app.
  • Keyboard shortcuts use one document-level capture listener, keyed by a stable .NET GUID token, never the root element. A detached root revives as null server-side and leaked the entire subtree.

CSS contract: every absolute font-size becomes font-size: calc(Npx * var(--fx-zoom, 1)). Values in em, inherit, % or 0 are deliberately not wrapped — they scale via the root em base already. Variable definitions stay plain; consumers get wrapped. Any new font-size rule must use the calc pattern or be inherit-based.

Layout traps found during the port

A page's own CSS must be swept too — page-level .razor.css, inline style= attributes and in-file <style> blocks stay at fixed px otherwise, leaving chrome unzoomed.

Wrapping a CSS grid container shifts every band by one row. This is exactly why the FMain wrapper uses Style="display:contents" — that wrapper never becomes a grid or flex item.

At high zoom, fixed-width label columns clip. That is expected under the "dimensions never change" spec, not a bug.

Zoom is not persisted — it resets to 100% per circuit. Wiring it through the per-user preferences store is the obvious follow-up.

HomeFrontPB / HomeFront App

The two applications share migrated VB6 forms — Components/Pages/Migrated/F*.razor in HomeFront, flat Components/Pages/F*.razor in HomeFrontPB — but since 2026-08-28 the sync is ONE-WAY: PB → HF only. There is no HF → PB flow of any kind: HomeFrontPB is going away yet still under test, so its tree must not be disturbed, and new work lands in HomeFront. Both apps carry the same @namespace line, so strip it (and trailing-newline noise) before comparing or the diff inflates with false positives. 19 of 127 shared page files differ, much of it deliberate — FFeedback, Workflow/WorkflowEstimating, FInboxCustomQuote, FSendingWizard. Do not reconcile those.

FMain.razor is the exception — roughly 1,700 lines of long-standing drift. Hand-apply changes there; never copy wholesale.

The rules that govern form work

  • VB6 fidelity is the prime directive. Read the matching .frm or .bas under HomeFrontVB6/ before changing a migrated page. Most bugs are translation errors, not design flaws — HHM-829 turned on exactly this, where VB6 auto-sizes a grid the migration hardcoded.
  • Grid columns come from AppGridLayout (IniGetGrid → GetGridLayoutAsync), rendered dynamically. Never hardcode a migrated page's column list or widths.
  • All UI primitives come from FlexKit. A raw <input>, <select> or <div> modal is a red flag — create the missing primitive in the library instead.
  • Minimise JavaScript. It needs a genuine DOM-only justification, a tiny lazy import and a graceful C# fallback, and it gets flagged when added.
  • Never interpolate user values into SQL. Always parameterise.
